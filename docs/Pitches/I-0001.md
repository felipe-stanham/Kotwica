# Pitch: Home DDNS + Cert Watch (Latarnia App)

**ID:** I-0001
**Date:** 2026-10-08
**Status:** Ready for Promotion

> Hand-off note: this pitch was shaped inside the Latarnia repo but the App will
> live in its own repository. It uses Latarnia's Ubiquitous Language (App,
> Service App, Manifest, Secret, Health Check). The last section ("Context for
> the new repo") carries the facts the new repo will not have.

---

## Problem

`home.stanham.com` is the public name for both Latarnia environments on the
Raspberry Pi (tst on :8443, prd on :443). Today it is a CNAME to
`stanham.tplinkdns.com`, the DDNS name the TP-Link router keeps updated with the
home's dynamic public IP.

That chain broke silently:

- TP-Link's authoritative nameservers now answer NXDOMAIN to anything except the
  A record. That includes the AAAA query for the host, the NS/SOA of their own
  zone, and the names of their own nameservers. Strict resolvers such as Google
  8.8.8.8 (seen from Europe) and Let's Encrypt's then treat the whole name as
  non-existent.
- Caddy's certificate renewal for `home.stanham.com` started failing about
  2026-08-10. The cert expired on 2026-09-09. Caddy's storage cleaner deleted it
  on 2026-09-24.
- **No one noticed for 7 weeks.** The failures were only visible in Caddy's
  journal. Latarnia's dashboard showed everything green, because the platform
  and its Apps were healthy behind a dead front door.
- As of 2026-10-08 the Pi serves no certificate at all, so HTTPS to both tst and
  prd on the Pi fails. The home IP has also changed: it was 186.54.87.5 on
  2026-09-29 and is 167.60.249.130 on 2026-10-08. A hand-set A record would go
  stale the same way.

There are two pains:

1. **The DNS name depends on a provider we do not control and that is
   misbehaving.**
2. **Certificate or DNS breakage is invisible.** Nothing in Latarnia surfaces it.

## Appetite

Small batch, a few days. It is a utility App with one job and a watchdog. If
it grows beyond that, stop and reconsider.

## Solution

A Latarnia **Service App** that runs on the Pi's prd environment and does two
things on a schedule:

1. **Keeps the DNS record current.** It detects the home's current public IP.
   If that differs from the `home` A record at GoDaddy (the DNS provider for
   `stanham.com`), it updates the record through the GoDaddy API. The CNAME to
   tplinkdns is replaced by an A record that this App owns.
2. **Watches what the outside world sees.** For each Watched Host it checks
   that:
   - the name resolves to the expected IP through more than one public
     resolver, including a strict one;
   - the TLS certificate being served is valid;
   - the certificate does not expire soon.

The result is reported through the App's `/health`, so it shows on the Latarnia
dashboard like any other App:

- `good`: DNS matches the current IP and the cert has more than 14 days left.
- `warning`: the cert has 14 days or fewer left, the last DNS update failed but
  is retrying, or one resolver disagrees.
- `error`: the cert expires within 3 days or is already invalid, DNS points to a
  wrong IP, or the GoDaddy API rejects the credentials.

Flow, at fat-marker level:

    every N minutes:
      current_ip = what the internet sees as our IP
      record_ip  = GoDaddy A record for home.stanham.com
      if current_ip != record_ip -> update GoDaddy, log it
      for each Watched Host:
        resolve via several public resolvers -> compare to expected IP
        open TLS -> read cert expiry
      publish state -> /health (+ a small status page)

## Boundaries

### IN Scope
- Updating one A record (`home.stanham.com`) at GoDaddy when the public IP
  changes.
- Watching DNS resolution and TLS certificate validity and expiry for a
  configurable list of hostnames. At minimum `home.stanham.com:443` and
  `home.stanham.com:8443`; optionally `latarnia-1.stanham.com`.
- Reporting state via `/health` (`good` / `warning` / `error`) with a short
  human-readable `message`.
- Storing the GoDaddy Personal Access Token as a Latarnia Secret
  (`GODADDY_API_TOKEN`) via `requires_secrets`.
- A minimal read-only status view: last IP, last update, per-host cert expiry,
  last error.

### OUT of Scope
- No certificate issuance or renewal. Caddy stays the only ACME client; this App
  only observes.
- No DNS providers other than GoDaddy in v1.
- No IPv6 (AAAA) management in v1. The home connection is IPv4-only today.
- No alerting channels (email, push, Slack) in v1. The Latarnia dashboard and
  `/health` are the signal.
- No management of any record other than the configured A record. The App must
  never touch MX, the apex, or other `stanham.com` records.
- Not run in tst, so there is exactly one writer of the DNS record.

### Cut List
1. Status page / UI. `/health` alone is enough.
2. Multi-resolver comparison. A single strict resolver (8.8.8.8) is enough.
3. Watching `latarnia-1.stanham.com`. It has a static IP and works today.

## Risks & Rabbit Holes

- **GoDaddy API access.** Validated on 2026-10-08: a read-only GET of the
  `home` A record with a production Personal Access Token (Bearer) returned
  HTTP 200. GoDaddy now issues Personal Access Tokens instead of key + secret;
  the legacy `sso-key` format is scheduled for deprecation in 2026, so use
  Bearer only.
- **Token expiry.** The token expires (the test token: 1 year) and can be
  revoked. A rejected token must surface as `error` with a message that says
  the token needs renewing.
- **GoDaddy minimum TTL is 600 s.** After an IP change, expect up to about 10
  minutes of stale resolution. Acceptable, but say so in the docs. The
  hand-set record currently has TTL 3600; the App should write 600.
- **Public-IP detection** depends on a third-party echo service (ipify or
  similar). Use two and require them to agree, but don't build a framework
  around it.
- **Chicken-and-egg on first switch.** Replacing the CNAME with the A record is
  a one-time manual or first-run step. After it, Caddy must be restarted on the
  Pi to obtain a fresh cert. Caddy is currently stuck with no cert in storage.
- **Do not over-engineer the watchdog** into a general uptime monitor. It
  watches our own hostnames, nothing else.
- **Watching from the Pi itself.** TLS checks connect to the Pi locally with
  SNI set to the hostname, which avoids depending on the router's hairpin NAT
  and needs no Caddy change. Blind spot: this does not prove the router's port
  forward works from the internet. Accepted for v1.
- **Running on the host it monitors.** If the Pi is down, the App is down too.
  Accepted for v1. The dashboard going dark is itself the signal. A second
  vantage point (for example Hetzner) is a later idea.

## Open Questions

Resolved on 2026-10-08:

- GoDaddy API access: yes, with a production Personal Access Token (HTTP 200).
- Watch `latarnia-1.stanham.com`: not in v1. Watched Hosts run on the Pi only.
- Interim fix: the `home` A record was set by hand to the current Public IP and
  the tplinkdns CNAME removed. Caddy must be restarted on the Pi to get a cert.
- Alerting outside the dashboard: no, not in v1.
- Glossary: Public IP and Watched Host added to `docs/System/glossary.md`.

Still open:

- Token scope for production: the test token has every DNS scope. Which
  minimum scope set do the GET and PUT on the A record need?

## No-Gos

- Do not let the App obtain or renew certificates, or edit Caddy config. Caddy
  owns TLS.
- Do not give the App write access to any DNS record beyond the one configured
  A record.
- Do not log the GoDaddy token or full API responses.
- Do not deploy it to more than one environment at a time (single writer).
- Do not add a database. A small JSON state file in the App's data dir is
  enough.

## Context for the new repo (facts from Latarnia, 2026-10-08)

- **App contract:** `latarnia.json` Manifest with `"type": "service"`,
  `requirements.txt`, and a `GET /health` endpoint returning
  `{"health": "good|warning|error", "message": "..."}`. Full contract:
  `docs/System/app-specification.md` in the Latarnia repo.
- **Secrets:** declare `config.requires_secrets`, i.e.
  `["GODADDY_API_TOKEN"]`. The operator adds the values to
  `/opt/latarnia/prd/secrets.env` (mode 600) on the Pi. The platform refuses to
  start the App if a declared Secret is missing. Watch out: stale per-app secret
  files are not cleaned up (Latarnia T-0014).
- **Ports:** do not declare them. Latarnia allocates them (prd REST 8150–8199).
- **Hosts:** Pi `homeserver` runs tst + prd behind `home.stanham.com`.
  `hetzner-latarnia-1` runs prd only, behind `latarnia-1.stanham.com` (static IP
  204.168.152.105, cert valid to 2026-11-01).
- **How we confirmed the DNS fault:**
  - `dig home.stanham.com @8.8.8.8` from the Hetzner box returns NXDOMAIN.
  - `dig ns1.tplinkdns.com A @52.204.177.89 +norec` returns NXDOMAIN with the
    `aa` flag.
  - From Uruguay, 1.1.1.1 and 8.8.8.8 look fine, which hides the problem.
- **Recovery after the DNS switch:** on the Pi, `sudo systemctl restart caddy`,
  then `sudo journalctl -u caddy -f` and look for "certificate obtained
  successfully".
